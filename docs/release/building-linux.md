# Reproducible Linux build guide

Linux artifacts must be built on Linux x86-64. Do not cross-build the runtime,
PTY native library, or installers from Windows or macOS.

## Pinned toolchain

- Node.js 24
- pnpm 11.9.0
- JDK 21
- the checked-in Maven wrapper

Install JavaScript dependencies with the lockfile:

```bash
pnpm install --frozen-lockfile
```

Run the complete deterministic gate:

```bash
pnpm verify
```

`pnpm build` creates the shaded worker JAR through Maven and runs the Maven
`runtime-image` profile. That profile uses `jlink` with the explicitly reviewed
module set in `apps/worker/pom.xml`. `pnpm test:runtime` launches integration
tests with that image, not the system JDK.

The desktop production graph pins `bash-language-server@5.6.0`. Electron's
embedded Node runtime launches its CLI under Java's bounded LSP ownership; no
global Node or language-server installation is needed. Packaging verification
checks the CLI/WASM assets, generated SBOM and license notices, and a real
Monaco language session from the unpacked application.

Create an unpacked native application and prove the packaged runtime path:

```bash
pnpm pack:dir
pnpm test:packaged
```

Create the three Linux candidates:

```bash
pnpm dist:linux
```

This command generates and verifies:

- AppImage, deb, and rpm candidates under `release/`;
- `release/SHA256SUMS.txt`, covering every candidate and metadata file;
- Java, Node, and combined CycloneDX 1.6 JSON SBOMs;
- complete generated third-party notices and downloaded Java license texts;
- the exact bundled Java runtime module inventory.

The same metadata is embedded under the installed application's
`resources/metadata` directory. `pnpm release:verify
--require-linux-packages` independently checks manifest coverage, every
SHA-256 digest, package magic bytes, SBOM graph integrity, attribution
coverage, deterministic formatting, and local-path leakage.

The application icon is generated by electron-builder from the reviewed
repository-native `apps/desktop/assets/packaging/icon.svg` master. Linux
installer smoke checks require the installed package to contain an SVG or PNG
desktop icon, and `desktopName` is synchronized with the generated desktop
entry so launchers can associate the running window with that icon.

The `linux-release` GitHub Actions workflow builds on a native Ubuntu 24.04
x86-64 VM. It launches the unpacked app and AppImage, then installs, launches,
and uninstalls the deb on fresh Ubuntu 24.04 and Ubuntu 26.04 hosted VMs. A
Fedora 44 container performs the equivalent rpm check as an unprivileged
desktop user. Fedora clean-VM evidence is still required before publication;
the container job is an early compatibility gate, not a substitute for that
release record.

Every installed-app smoke records the production React Flow render time and
zoom p95 for a 1,000-node canvas under Xvfb. The native build gate and each
installed deb/rpm job also stream 4 MiB through a real Pty4J session and framed
JSON-RPC using the candidate's bundled jlink runtime and worker. Both probes
enforce the ceilings in `docs/architecture/performance-budgets.md`, print the
observed values, and persist machine-readable probe results.

After uninstall and user-data-preservation checks succeed, each target creates
a strict native acceptance record. The record binds the tested package's file
name and SHA-256, package format, installed checks, measured canvas and PTY
values, and target identity to the exact 40-character `GITHUB_SHA`. A final
workflow job downloads all target records and runs:

```bash
node scripts/verify-native-acceptance-records.mjs \
  --records-dir native-acceptance \
  --expected-revision "$GITHUB_SHA"
```

The verifier requires exactly one valid record for Ubuntu 24.04 deb, Ubuntu
26.04 deb, and Fedora 44 rpm. It rejects symbolic links, unexpected fields,
duplicate or missing targets, mixed revisions, incomplete checks, and
out-of-budget measurements. The verified set is published as the
`command-ide-native-acceptance-records` workflow artifact.

Release publication remains blocked until the workflow and the clean-VM
release checklist pass. Never publish an artifact built from a dirty or
unrecorded source state.

## Verification record

Record the source commit, runner image, JDK/Node/pnpm versions, artifact SHA-256
values, packaged runtime module list, installer smoke result, large-canvas
render/zoom values, PTY MiB/s value, and any skipped native PTY test. Uninstall
tests must confirm that application binaries are removed without deleting the
user's data directory or exported projects. Retain the verified structured
acceptance artifact alongside the workflow log and release candidates; the
record is not valid for a different source revision.

The build deliberately uses the checked-in Maven wrapper for every Java task.
There is no Gradle build or required global Maven installation.
